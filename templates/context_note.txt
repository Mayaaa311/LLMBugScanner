Integer Overflow
        dataname: CVE-2018-14002
        code: 
        function distribute(address[] _addresses, uint[] _amounts) public returns (bool success) {
            require(_addresses.length < 256 && _addresses.length == _amounts.length);
            uint totalAmount;
            for (uint a = 0; a < _amounts.length; a++) {
                totalAmount += _amounts[a]; // Vulnerable line
            }
            require(totalAmount > 0 && balances[msg.sender] >= totalAmount);
            balances[msg.sender] -= totalAmount;
            for (uint b = 0; b < _addresses.length; b++) {
                if (_amounts[b] > 0) {
                    balances[_addresses[b]] += _amounts[b];
                    Transfer(msg.sender, _addresses[b], _amounts[b]);
                }
            }
            return true;
        }
        Vulnerable Function Name: distribute
        Reason: The vulnerability exists in the distribute function at the line: totalAmount += _amounts[a]; 
        This line adds up all elements in the _amounts array into the totalAmount variable. If the sum of _amounts[a] exceeds the maximum value representable by the uint type (2^256 - 1 in Solidity), it causes an integer overflow. Once the overflow occurs, the totalAmount wraps around to 0 or another unexpected value, bypassing the subsequent require check that ensures totalAmount > 0 && balances[msg.sender] >= totalAmount. This flaw can be exploited by an attacker who passes a maliciously crafted _amounts array that triggers the overflow. As a result, the require statement may pass even when the actual totalAmount exceeds the sender's balance, allowing the function to incorrectly deduct an invalid totalAmount from balances[msg.sender]. This deduction could lead to logical inconsistencies or even negative balances in the system. Moreover, an attacker could manipulate the token distribution, either distributing far more tokens than intended or causing a significant loss of funds for the sender. The impact of this vulnerability is severe because it directly undermines the integrity of the contract, leading to financial losses, incorrect token distributions, and reputational damage to the system. Without proper safeguards, the contract becomes vulnerable to exploits that could compromise its users and erode trust in its functionality.


Wrong Logic

        Dataname: CVE-2018-10468
        code: 
        function transferFrom(address _from, address _to, uint256 _value) returns (bool success) {
            if (msg.data.length < (3 * 32) + 4) { throw; }
            if (_value == 0) { return false; }
            uint256 fromBalance = balances[_from];
            uint256 allowance = allowed[_from][msg.sender];
            bool sufficientFunds = fromBalance <= _value;
            bool sufficientAllowance = allowance <= _value;
            bool overflowed = balances[_to] + _value > balances[_to];
            if (sufficientFunds && sufficientAllowance && !overflowed) {
                balances[_to] += _value;
                balances[_from] -= _value;
                allowed[_from][msg.sender] -= _value;
                Transfer(_from, _to, _value);
                return true;
            } else { 
                return false; 
            }
        }

        Vulnerable Function Name: transferFrom
        Description: The vulnerability in the transferFrom function arises from incorrectly implemented logic checks, leading to unexpected and unauthorized behavior. Specifically, the conditions for verifying sufficient funds and allowances are reversed. The line bool sufficientFunds = fromBalance <= _value; erroneously checks if the sender's balance is less than or equal to the transfer amount, instead of ensuring the balance is greater than or equal to the transfer amount. Similarly, the condition bool sufficientAllowance = allowance <= _value; incorrectly evaluates whether the allowance is less than or equal to the transfer amount, rather than confirming it is sufficient. These logical errors result in the function allowing transfers only when the sender's balance or allowance is insufficient, which is the exact opposite of the intended functionality. While the overflow check (bool overflowed = balances[_to] + _value > balances[_to];) is implemented correctly, it does not mitigate the consequences of the flawed logic checks. As a result, the function can be exploited to perform unauthorized token transfers, bypassing the constraints that should prevent such actions. This vulnerability poses a severe security risk, as it enables attackers to transfer tokens without proper permissions, leading to potential financial loss for users and undermining the contract's credibility. 


Access control: 

        Dataname: CVE-2018-19831
        code: 
        function ToOwner() public {
            balances[msg.sender] = totalSupply;               
            owner = msg.sender;
        }

        Vulnerable Function Name: ToOwner
        Description: The ToOwner function contains an access control vulnerability, allowing unauthorized users to gain control of the contract. This function assigns the entire token supply to the caller's balance and sets the caller as the contract's owner without any access control checks. Specifically, the function lacks a require statement or a similar mechanism to ensure that only the legitimate contract owner can call this function. Consequently, any user can invoke ToOwner, immediately gaining ownership of all tokens and control over the contract. This vulnerability poses a critical security risk. By exploiting it, an attacker can reassign ownership of the contract, gain access to functions restricted to the owner, and manipulate token distribution, effectively taking full control of the token economy. The impact includes complete loss of funds for legitimate users, irreparable damage to the contract's functionality, and severe harm to its credibility. This highlights the necessity of implementing robust access control mechanisms, such as modifiers (onlyOwner) or explicit require checks, to safeguard sensitive contract operations.


Token Devalue:
        Dataname: CVE-2018-12084
        code: 
        function mintToken(address target, uint256 mintedAmount) onlyOwner {
            balanceOf[target] += mintedAmount;
            totalSupply += mintedAmount;
            Transfer(0, this, mintedAmount);
            Transfer(this, target, mintedAmount);
        }

        Vulnerable Function Name: mintToken
        Description: The mintToken function in the BitAseanToken contract exhibits a token devalue vulnerability. This function allows the contract owner to mint arbitrary amounts of tokens and assign them to any target address. While the function is restricted to the owner using the onlyOwner modifier, it lacks mechanisms to limit the maximum amount of tokens that can be minted. The absence of constraints enables the owner to generate excessive tokens, which can disrupt the token’s supply-demand balance and compromise its value.

        This vulnerability poses a significant risk because it grants unchecked control over token issuance to a single entity. The owner can arbitrarily inflate the total supply, potentially devaluing existing tokens and undermining trust in the token’s integrity. The impact of this issue is twofold: financially, it can lead to token price crashes, causing losses for holders; reputationally, it erodes trust among investors and the broader market.

        To mitigate this vulnerability, safeguards should be implemented, such as:

        Setting a maximum cap on total supply.
        Introducing a multi-signature mechanism for minting to require multiple approvals.
        Adding transparency by logging minting events and publishing them for stakeholder review.
        Without these measures, the contract remains vulnerable to misuse, which can severely damage the token’s ecosystem.



Bad randomness:

        Dataname: CVE-2018-15552
        code:
            function PayWinner(address winner) private { 
                require(numtickets == maxTickets);
                uint ownerTax = 6 * totalBounty / 100;
                uint winnerPrice = totalBounty - ownerTax;
                LottoComplete(msg.sender, lottoIndex, winnerPrice);
                lottoIndex += 1;
                numtickets = 0;
                totalBounty = 0;
                if (_direction == 0 && maxTickets < 20) maxTickets += 1;
                if (_direction == 1 && maxTickets > 10) maxTickets -= 1;
                if (_direction == 0 && maxTickets == 20) _direction = 1;
                if (_direction == 1 && maxTickets == 10) _direction = 0;
                worldOwner.transfer(ownerTax);
                winner.transfer(winnerPrice); 
            }
        Vulnerable Function Name: PayWinner
        Description: The PayWinner function in the LottoCount contract exhibits a bad randomness vulnerability, as it lacks a secure mechanism for selecting the lottery winner. The function deterministically awards the prize to the msg.sender of the final ticket purchase when the total number of tickets (numtickets) reaches maxTickets. This logic is entirely predictable, allowing a malicious user to monitor blockchain activity and strategically buy the last ticket, ensuring they become the winner. Without a cryptographic random number generator, the process is not truly random and can be manipulated. This predictability compromises the fairness of the lottery, enabling attackers to exploit the system repeatedly to win multiple lotteries. Consequently, legitimate participants lose funds, and the perceived integrity of the contract is undermined. Beyond financial losses for players, this vulnerability also causes reputational damage to the contract, as users perceive it as insecure and unfair. To address this issue, the selection process should involve a secure and unpredictable random number generation method. Using block attributes combined with user inputs, or integrating external randomness solutions like Chainlink VRF, can ensure fairness and tamper-proof winner selection. Additionally, introducing a delay between the final ticket purchase and winner announcement, leveraging verifiable randomness after the block is mined, would further enhance the lottery's security and trustworthiness.

Typo Constructor:
        Dataname: CVE-2019-15080
        code:
            function MorphToken() 
                ERC20 (tokenSupply, "MORPH", "MORPH") public 
            {
                owner = msg.sender;
            }


        Vulnerable Function Name:  MorphToken
        Description: The vulnerability in this contract arises from a Typo Constructor issue in the function named MorphToken, which serves as the constructor for the MorphToken contract. In earlier versions of Solidity (prior to 0.5.0), constructors are functions with the same name as the contract itself. This approach, while functional, is highly error-prone, as a minor typographical error in the function name can result in the function being treated as a regular public function instead of a constructor. Consequently, anyone can invoke it, potentially causing unintended behavior.

            In this contract, the MorphToken function is correctly named to match the contract name, but its reliance on an outdated and risky naming convention introduces significant security concerns. If developers or maintainers make a mistake during upgrades or refactoring and inadvertently alter the constructor's name, the function might become publicly accessible. This could allow malicious actors to execute critical initialization logic or reinitialize the contract's state, leading to misconfigurations, unauthorized minting of tokens, or complete takeover of the contract.

            The effects of this vulnerability are severe and could result in a Denial of Service (DoS) scenario. An attacker could exploit this misconfiguration to disrupt contract functionality, invalidate assumptions about the state, or drain the contract's resources. To mitigate this, Solidity versions 0.5.0 and later enforce explicit use of the constructor keyword for defining constructors, making them unambiguously identifiable and preventing such errors. Upgrading the contract to use modern Solidity syntax is essential to address this vulnerability and improve overall code safety and reliability.
                
                

Denial of Services:

        code:
                    // SPDX-License-Identifier: MIT
                    pragma solidity ^0.8.13;

                    contract KingOfEther {
                        address public king;
                        uint public king;

                        function claimThrone() external payable {
                            require(msg.value > balance,"Need to pay more to become the king");

                            (bool sent,) = king.call{value:balance}("");
                            require(sent,"Failed to send Ether");

                            balance = msg.value;
                            king = msg.sender;
                        }
                    }
        function name: claimThrone()
        Description: The vulnerability in the KingOfEther contract arises from improper handling of refund logic in the claimThrone() function. This function processes two critical operations: crowning a new "King" and refunding the previous "King's" ether. The refund operation relies on the sent variable, which checks the success of the ether transfer and uses the require(sent, "Failed to send Ether") statement to ensure successful execution.

        The issue occurs when a malicious contract, such as the provided Attack contract, claims the throne and intentionally lacks a fallback() or receive() function to accept ether. As a result, any attempt to refund ether to the attacking contract fails, causing the sent variable to return false. This triggers the require statement to revert the transaction, preventing the function from executing further.

        The impact of this vulnerability is severe, as it creates a Denial of Service (DoS) condition in the KingOfEther contract. Once the attack contract becomes the "King," no subsequent player can claim the throne, effectively locking the contract and rendering it unusable. To mitigate this issue, the refund logic should be decoupled from critical state changes, and pull payment patterns or escrow mechanisms should be employed to handle refunds securely and prevent such attacks
